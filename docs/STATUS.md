# Capability status

_Verified against `main` at `65c144b` on 2026-09-15._

This repository is read before it is run, and its prose describes a few things the code
does not do. This file is the correction: one row per capability the documentation claims,
what is actually behind it at HEAD, and — where the answer is "not fully" — the PRD that
owns finishing it.

The rule that keeps it honest lives in `.context/conventions.md`: a capability claim in
`README.md`, `.context/` or `.agents/` must be true of the code at HEAD. Anything
aspirational either gets a row here or goes to `docs/prd/`. `yarn lint:docs` resolves every
`path:NN` citation below against the tracked tree and fails the build when one no longer
does.

## How to read the status column

| Status        | Means                                                                                                      |
| ------------- | ---------------------------------------------------------------------------------------------------------- |
| `implemented` | Wired into the running service and exercised by a test, a workflow, or a probe that ran on the date above. |
| `stubbed`     | The code exists and compiles, but nothing on a request path constructs or applies it.                      |
| `planned`     | Not built. The claim is forward-looking, or the row is what remains after a claim was removed.             |
| `broken`      | Built and reachable, but what it does today contradicts what the documentation says it does.               |
| `removed`     | Documented or provisioned, never used. The provisioning or the claim is gone.                              |
| `unverified`  | Built, but the author of this matrix could not run it. The row says what would verify it.                  |

Where a row is `implemented` and the evidence says "restated", the capability works and the
sentence describing it was too strong; the restatement is the sentence that is true.

## What this means for a reader

The primitives are real and tested: envelope encryption with AAD binding, a hash chain with
HMAC signatures, RFC 7807 everywhere, optimistic concurrency, PII redaction. Seventeen rows
are `implemented`, and the API's e2e suite passes against a real Postgres.

What the prose overstates is the production story. The KEK lives in a JSON file that the
published image copies into itself, and `CRYPTO_CORE_MODE=prod` cannot start (rows 5 and
6). The audit log is tamper-evident in a unit test and best-effort in the service (rows 10,
12, 13, 15), and every entry names the same nil actor (row 14). The console's front page
calls a route that does not exist (row 28). Three pieces of pipeline exist and are never
applied: the structured logger, response validation, the SBOM upload (rows 18, 22, 36).

Rows 9, 16, 20, 23, 38 and 39 have no owner. Rows 9, 16, 23 and 39 need none; row 20 is a
test nobody has written; row 38 is a deployment decision that no PRD has been asked to
make. Inventing an id for each would put rows in the backlog nobody has agreed to.

## Keeping this file true

Nothing lints prose. What keeps this file honest is that it is short, every row names a
file and a line, `yarn lint:docs` fails when a cited line is past the end of its file or the
file is gone, and `.context/conventions.md` requires a pull request that moves a row to move
it here in the same change. If a row's evidence no longer resolves, the row is wrong — fix it
rather than working around it.
